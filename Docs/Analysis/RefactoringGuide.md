# 리팩토링 가이드 (2026-10-28 개정)

현재 변경을 더 안전하고 단순하게 만드는 데 필요한 기법을 고르는 참고 문서다. 아래 기법을 모두 적용하는 것이 목표는 아니다.
예시의 항목 번호(A1, C3, J3 …)는 [ResponsibilityReview.md](ResponsibilityReview.md)의 점검 항목이다.

## 0. 적용 범위와 판단 기준

- 폴더·책임·의존 관계는 [Project README](../../Assets/Project/README.md)를 따른다. 현재 구조는 `Game → Systems` 두 어셈블리이며, GNM은 경기 생성·관리 연결과 Tick을 담당한다.
- 새 계층·통합 MatchHost·Gateway 도입이나 `Network/`에 코드 파일을 추가하는 것은 현행 규칙 안의 단순 정리가 아니다. 필요성과 대안을 설명하는 별도 구조 변경 제안으로 다룬다.
- 먼저 **확인된 결함 / 재현 필요 / 설계 결정 / 선택적 개선**을 구분한다. 코드 스멜은 조사 단서이며 버그나 변경 의무를 뜻하지 않는다.
- 변경마다 현재 실패 경로, 기대 효과, 가장 작은 수정, 확인 방법을 적는다. 메서드 정리나 참조 연결로 해결되면 새 클래스·인터페이스를 만들 필요가 없다.
- 구조를 나누면서 생기는 연결 설정·구독 수명·직렬화 이전·테스트 수정 비용도 계산한다. 클래스 수나 참조 수 감소만으로 성공을 판단하지 않는다.

## 1. 리팩토링이란

**정의**: 외부에서 관찰되는 동작을 보존하며 내부 구조를 바꾸는 것. 기능 추가와 버그 수정은 동작 변경으로 구분한다.

**원칙**

1. **동작 보존** — 순수 구조 변경은 전후 결과가 같아야 한다. 변경 범위에 맞는 기존 테스트·체크리스트를 확보한다.
2. **작은 단계** — 원인을 추적하고 되돌릴 수 있는 단위로 바꾸고 확인한다.
3. **목적 구분** — 동작 변경과 구조 정리를 리뷰에서 구별할 수 있게 한다. 독립적인 큰 정리는 커밋을 나누되, 작은 수정에 꼭 필요한 정리까지 기법별로 잘게 커밋할 의무는 없다.
4. **필요할 때** — 현재 수정·검증을 방해하는 구조부터 고친다. 프로젝트 전체의 패턴 통일을 선행조건으로 삼지 않는다.
5. **주변 정리의 범위 제한** — 지나간 코드의 개선도 이번 작업과 관련 있고 확인 가능한 범위에서 한다.

## 2. 언제: 코드 스멜을 조사 단서로 쓰기

| 단서 | 이 프로젝트에서 확인할 것 | 우선 고려할 작은 조치 |
|---|---|---|
| 큰 클래스·서로 다른 변경 이유 | D1·D2의 역할 중 실제로 독립 변경·재사용되는 부분이 있는가 | 관련 메서드를 묶고 이름을 정리한 뒤 필요할 때만 Extract Class |
| 같은 규칙의 사본 | C1·C3의 하한가·정원 등이 서로 어긋날 수 있는가 | 규칙값의 출처와 검증을 통일. UI 미리보기 계산은 유지 가능 |
| 내부 UI 경로 의존 | D5·G6에서 프리팹 변경 시 연결이 끊기거나 매번 탐색하는가 | 뷰 내부에서 참조 캐시·필수 연결 검증, 필요하면 직렬화 참조 |
| 뜻이 불명확한 값 | G1 응답 문자열로 요청 종류·결과를 구분할 수 없는가 | 필요한 결과 타입. I4의 정상 sentinel까지 일괄 교체하지 않음 |
| 의미를 반복해서 적는 숫자 | 변경 가능한 규칙인가, 고정 개수인가, 개별 에셋의 배치값인가 | 같은 의미의 상수·설정만 공유. 모든 리터럴을 설정으로 만들지 않음 |
| 함께 전달되는 값 | I5의 인자나 좌석 쌍을 잘못 조합하는 호출이 생기는가 | 이름·인자 묶음 검토. Mirror hook 순서 설명만으로 결함 판정하지 않음 |
| 초기화·활성화 순서 | D6의 최초 플레이어 탐색이 실제 생성 시점과 맞는가 | 올바른 시점에 참조 연결. I15의 에디터 직접 호출·반복 초기화 보장은 유지 |
| 미사용 코드·미통합 자산 | E2·E3가 폐기 대상인가, 예정 기능/Dev/직렬화에서 쓰이는가 | 사용처와 계획 확인 후 연결·유지·삭제 중 선택 |
| 전역 상태의 수명 | C2·G9에서 수신 전·종료·재접속 상태를 어떻게 표현하는가 | 소유·초기화·변경 알림 명확화. private setter인 캐시와 임의 쓰기 가능한 전역을 구분 |
| 불필요한 전체 갱신 | F6·J5에서 값이 안 바뀌어도 탐색·문자열·화면을 다시 만드는가 | 캐시·변경 비교·필요한 알림. 타이머·이동 폴링은 별도 판단 |

`GetComponentInParent` 한 번, `bool` 인자, 배열·문자열·직접 참조, 구현 하나인 인터페이스라는 사실만으로 문제를 확정하지 않는다. `ILocalMatch`는 현재 Dev 연결에 쓰이므로 사용하지 않는 확장 지점의 예가 아니다.

## 3. 기법 카탈로그 (필요한 것만 선택)

**작은 정리부터**: Extract Variable, Rename(직렬화 주의), Extract / Inline Function, Guard Clauses, 조건식 단순화, 중복 갱신 제거.

**데이터·API**: Encapsulate Variable / Collection, Introduce Parameter Object, 필요한 결과 타입, Separate Query from Modifier. 실제 잘못된 조합이나 규칙 우회 호출을 줄이는지 확인한다.

**클래스 간 이동**: Move Function / Field, Extract / Inline Class. 오브젝트별 배치와 의존 관계는 README를 따른다.

**다형성·State·Factory**: 같은 규칙의 변형이 반복되고 단순 함수·enum/switch로 관리하기 어려울 때 검토한다. Open/Secret 경매처럼 규칙이 다른 구현을 필드 모양이 비슷하다는 이유로 공통 부모에 묶지 않는다(I9~I11).

## 4. 설계 원칙의 적용 한계

- **응집도와 단일 책임** — 같이 바뀌는 일을 묶는다. 한 오브젝트의 여러 Command나 경기 수명 조정은 관련된 책임일 수 있다(D1·D2).
- **단일 진실 원천** — 규칙을 결정하는 곳을 명확히 한다. 서버 상태와 클라 사본, 도메인 배열과 전송 배열, 예상 금액 계산까지 모두 제거하라는 뜻은 아니다.
- **의존 방향** — `Systems`가 Unity·Mirror·UI에 의존하지 않는 현재 경계를 유지한다. Game 안의 양방향 타입 참조는 실제 수정 비용·서버/클라 접근을 보고 평가한다. 다섯 계층 도입은 기본 처방에서 제외한다(J1).
- **인터페이스·이벤트** — 교체·테스트·독립 수명에 이점이 있을 때 사용한다. 캐릭터가 UI를 직접 참조한다는 이유만으로 SO 이벤트 채널이나 인터페이스로 전부 바꾸지 않는다(D4).
- **Tell, Don't Ask / 디미터 법칙** — 다른 객체의 내부 규칙을 복제하지 않도록 살핀다. 동기화된 상태 조회와 일반적인 Unity 컴포넌트 조회까지 금지하지 않는다.
- **명령·조회 분리(CQS)** — 조회가 예상 밖의 외부 상태 변경을 일으키지 않게 한다. `TryReserve → bool`, `Close → 결과` 같은 변경+결과 반환은 유용한 API다. 외부에서 관찰할 수 없는 캐시 초기화도 따로 판단한다. [Fowler의 예외·관찰 가능한 상태 설명](https://martinfowler.com/bliki/CommandQuerySeparation.html)
- **YAGNI / KISS** — 현재 필요한 변경을 쉽게 만드는 정리는 하되, 미래 확장만을 위한 추가 복잡성을 피한다. [Fowler의 YAGNI와 리팩토링 구분](https://martinfowler.com/bliki/Yagni.html)

## 5. 변경 범위에 맞게 확인하기

**확인 방법**

- **EditMode** — 순수 규칙·계산의 입력과 결과를 검사한다. 실제 사용하지 않는 보조 클래스의 테스트를 런타임 보장으로 해석하지 않는다.
- **특성화 테스트** — 순수 구조 변경에서 보존할 현재 동작을 고정한다. 이미 확인된 버그는 기대 동작을 검증하는 회귀 테스트로 수정할 수 있으며, 잘못된 동작을 일부러 별도 테스트로 영구 고정할 필요는 없다.
- **PlayMode** — 현재 `HostedMatch`를 활용한다. private 필드를 옮기거나 이름을 바꿀 때 관련 테스트를 함께 고친다. 리플렉션 제거나 테스트용 API 신설이 모든 수정의 선행조건은 아니다(K8).
- **원격 클라** — 호스트가 숨기는 순서·동기화·다인 문제는 전용 서버와 실제 클라이언트로 확인한다. 기존 UDP 입장 검증도 활용하되, 그것이 아바타 hook·개별 UI까지 검증하지는 않는다.
- **수동 체크리스트** — 변경한 경로를 중심으로 입장 → 준비 → 시작 → 거래 → 착석 → 입찰 → 일어서기 → 결과/복귀를 확인한다.
- 검증 코드 존재, 이번 실행 여부, 통과 결과, 검증 범위를 구분해 기록한다. 과거 PASS 파일만으로 현재 동작을 보장하지 않는다.

**큰 변경일 때만 고려할 전략**

- **Parallel Change** — 새 경로 추가 → 호출부 이동 → 옛 경로 제거. 전환 중 두 방식의 불일치도 관리해야 한다.
- **Branch by Abstraction / 점진적 교체** — 실제로 큰 구현 교체가 필요할 때 선택한다. 작은 수정에 임시 인터페이스를 먼저 만들 필요는 없다.
- **Mikado Method / Seam** — 선행 의존이나 테스트 곤란이 작업을 막을 때 활용한다. 테스트 지점은 함수 인자·시계 분리만으로 충분할 수도 있다.

**작업 습관**

- 커밋은 검토·롤백 가능한 목적 단위로 만든다. 큰 포맷 변경과 동작 변경은 구분한다.
- IDE Rename·Extract Method를 활용하되 Unity 에셋·JSON·네트워크 이름 참조를 별도로 확인한다.
- 필요한 확인이 통과하면 범위를 마친다. 무관한 클래스 분리·테스트 체계 개편을 계속 추가하지 않는다.

## 6. Unity 특화

**직렬화와 이름 변경**

- 저장된 `[SerializeField]` 이름을 바꿀 때는 `[FormerlySerializedAs]` 등 이전 값을 보존하는 절차를 쓴다. 기존 속성을 제거할 때도 과거 에셋·브랜치 호환 필요를 확인한다.
- MonoBehaviour의 클래스명·파일명과 `.meta` GUID를 유지·이전하고, 변경한 `.prefab`·`.unity` 및 Missing Script를 확인한다.
- 네임스페이스·어셈블리를 바꾸면 `[SerializeReference]` 등 저장된 타입과 UnityEvent 대상 타입의 이전 필요를 확인한다. 필요한 경우 `[MovedFrom]`을 적용한다(J3).
- Animator 이름·enum 정수값·UnityEvent 메서드명·JSON 키·씬 이름은 **해당 대상을 바꾸는 작업에서** 에셋과 함께 확인한다. 모든 이름을 먼저 상수화할 의무는 없다.
- Animator 해시는 문자열 중복·호출 비용을 줄일 수 있지만 에셋의 파라미터 존재를 보장하지 않는다. 직렬화된 enum은 기존 숫자를 보존하고, 명시 값을 도입한다면 현재 에셋과 일치시킨다.
- UnityEvent는 Inspector 연결을 위한 정상적인 선택이다. 이름 변경 시 연결 검증과 코드 구독 중 비용이 작은 방법을 고른다. [Unity 공식 설명](https://docs.unity3d.com/6000.2/Documentation/Manual/unity-events.html)

**구조와 프레임 갱신**

- **순수 C# 추출** — 계산이 복잡하거나 독립 테스트가 필요할 때 한다. 단순 Unity 연결 코드는 MonoBehaviour에 둬도 된다(J2).
- **View/Presenter** — README대로 로직이 커질 때만 분리한다. 화면의 예상 비용·수량 계산을 반드시 서버로 옮길 필요는 없다(C1).
- **참조** — 의미가 특정된 Animator·외부 패널은 명시적으로 연결·검증한다. 같은 오브젝트의 필수 컴포넌트 확보나 의도적인 절차적 생성은 허용한다(G5).
- **초기화** — Awake 외에 에디터 직접 호출·비활성 오브젝트 사용이 있는지 확인한다. 현재 Door·Rope의 반복 호출 가능한 Initialize를 무조건 제거하지 않는다(I15).
- **설정** — 현재 경기 규칙 JSON을 활용한다. SO는 Inspector 편집·공유 에셋이 필요할 때 검토한다. 동일한 리터럴이나 프리팹 기본값이 있다는 이유만으로 SO·variant를 의무화하지 않는다(C3·G7·J4).
- **이벤트와 폴링** — 드문 상태 변화에는 알림·변경 비교를, 타이머·입력·이동에는 필요한 주기 갱신을 쓴다. 구독을 쓰면 수명·초기 상태·해제를 함께 처리한다(F6·J5).

## 7. Mirror(네트워크) 특화

- **서버 권위** — 가격·입찰 자격·좌석의 유효성을 서버가 최종 검증한다. 거래 장소 검증과 이동 검증 범위는 규칙·신뢰 모델에 맞춰 정한다(B1·B2·K4). UI의 버튼 활성화·예상 결과는 클라에서 계산할 수 있다(B5·C1).
- **Command 검증·응답** — 범위·소유권·경기 상태를 확인한다. 사용자에게 설명할 실패는 응답하되, 이미 서 있는 플레이어의 Stand처럼 멱등적인 요청까지 매번 오류로 만들 필요는 없다(K5).
- **상태와 이벤트** — 지속 상태는 초기 수신·늦은 구독·재접속 경로까지 설계한다. SyncVar/SyncList가 기본 선택이며, Rpc를 쓰면 캐시·초기 전송을 확인한다. Owner 동기화로 받는 개인 상태도 늦은 UI 활성화 시 캐시에서 복원한다(G2).
- **비공개 정보** — Owner 동기화·수신자 제한으로 보호한다. 불필요한 전원 갱신은 활동 시점의 단서를 줄 수 있으나, 그것만으로 요청자 신원·요청 종류가 드러난다고 단정하지 않는다(F7·K1).
- **실행 위치** — 연출과 서버 상태 처리를 구분한다. 서버의 필수 초기화까지 일괄 `isClient` 가드로 건너뛰지 않게 한다(G8).
- **재접속** — 지원하기로 한 범위에서는 연결과 무관한 PlayerId·복원 절차가 필요하다. 이탈 시 입찰 취소·예약 해제 여부는 별도 정책이며 자동 취소를 기본값으로 삼지 않는다(F3·F4).
- **직렬화 호환** — 현재 Mirror의 메시지 ID는 타입 FullName, Command/Rpc ID는 메서드 FullName에 기반한다. 파일 이동만으로는 바뀌지 않는다. 타입·메서드명·네임스페이스·전송 필드·enum 변경 시 호환성과 프로토콜 버전을 함께 확인한다(K6).
- **SyncList** — Clear/Add는 같은 값이어도 변경 op를 만든다. 값 비교·인덱서 갱신으로 불필요한 전송을 줄이고, 클라가 갱신 도중의 불완전한 상태를 읽지 않도록 확인한다(K1·F6).

## 8. 피해야 할 것

- 결함을 고치기 전에 프로젝트 전체를 재구성하는 것.
- 코드 스멜 이름을 붙인 뒤 재현 경로·현재 역할·더 작은 대안 없이 클래스를 나누는 것.
- 직접 참조를 모두 이벤트로, 조건문을 모두 다형성으로, 숫자를 모두 설정으로 바꾸는 것.
- 구현 개수만으로 인터페이스의 가치를 판단하는 것. 현재 의존 경계나 테스트에 필요한 구현 하나의 인터페이스도 있을 수 있다.
- 검증 없이 큰 이동을 하거나, 작은 수정의 안전망을 이유로 무관한 테스트 기반 전체를 먼저 개편하는 것.
- 현재 배치를 정당화하려고 README를 자동으로 구현에 맞추는 것. 규칙 변경은 필요성과 대안을 따로 제안한다.
